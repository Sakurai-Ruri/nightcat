# 同刻之地（Companion Places）

> 状态：**已登记，未排期**。功能归属建议 V0.7「趣味层」，不进入 V0。
> 登记日期：第 3 步之后。本文件是这份需求的**唯一权威描述**，聊天记录不算。

## 1. 需求原话（保留原始表述，避免转述走样）

> 有一个功能是我一定想要的（不一定是现在，只是别忘了这个目标），有一行字现实：你现在生活在（时区），可能的地点是（该时区对应的国家，城市，选择比较出名的城市），而且这个国家城市会有一个列表可以随机出现，然后点进去可以获得改时区/国家/城市的介绍

## 2. 产品意图

NightCat 的主线是"世界的时钟与你的作息错位"。这个功能是同一主题的**另一半**：

- 主线回答"**现在对我来说是几点**"（时间被重新映射到个人作息）。
- 这个功能回答"**和我读同一个钟表的，还有哪些地方**"（空间被映射到同一个时区）。

它不参与任何计算，是**纯趣味与认知层**。价值在于那个反直觉的事实：同一个钟表读数，对应着地球上从北京到珀斯的整片区域——而你通常只把它当作"我的时区"。

中文名「同刻之地」是暂定名，可改。

## 3. 交互规格（三层）

```text
第 1 层（一行字）      你现在生活在 UTC+8 · 可能的地点：新加坡        [换一个]
                          ↑ 时区以设备为准      ↑ 随机，点它可展开
第 2 层（点击后展开）  该 UTC 偏移下的城市列表 + 每个地方当前的钟表读数
第 3 层（点某个城市）  时区 / 国家或地区 / 城市介绍  ← 当前阶段为占位
```

要点：

- 第 1 层常驻在主卡片下方，一行，不抢主信息的视觉权重。
- 「换一个」按钮只在同一偏移的城市列表里重新抽，不跨时区。
- 第 3 层的**介绍文字当前为占位**（见 §6），但结构要先立起来，避免以后返工。

## 4. 已决定的四项（附理由与后果）

| # | 决定 | 理由 | 已知后果 / 缓解 |
| --- | --- | --- | --- |
| 1 | 时区**以设备/浏览器为准** | 最省事，用户不需要先设置任何东西 | ⚠️ **与 Location 可能不一致**：若用户手选的城市在别的时区（例如人在 UTC+8 却把位置设成伦敦看日照），这一行说 UTC+8，日照卡片说伦敦。**缓解**：两者不一致时给一句轻提示（"你的位置设置为伦敦，与设备时区不同"），不隐藏矛盾、也不擅自替用户改 |
| 2 | 地点列表**按 UTC 偏移**组织 | 同一偏移横跨多国，列表丰富，"世界上还有这些地方和你同刻"这个趣味点最强 | 偏移相同的地区被并列，需要一条**文案口径**（见 §7） |
| 3 | **每个个人日**换一次，另给「换一个」手动抽 | 与 PersonalDay 概念一致（起床即换新的一天），同一天内不会反复变，可复述、可截图分享 | 需要"确定性随机"的实现，见 §5 |
| 4 | 介绍内容**先做占位** | 先立结构与交互，文案后补，避免数据准备阻塞功能 | 第 3 层暂时只有时区/地区/城市名 + 当地钟表读数 |

## 5. 实现设计（关键：确定性随机）

**不要"抽一次然后存起来"。** 那样每换一个存储实现都要多存一个字段，而且刷新与多标签页之间会不一致。

正确做法是把选择变成**纯函数**：

```ts
// src/domain/companionPlaces.ts（纯计算，可用 node --test 验证）
pickPlaceForDay(places: Place[], utcOffsetMinutes: number, seed: string, rerollCount: number): Place | null
```

- `seed` 用**本个人日的起点日期**（`personalDayStart`，已由 `PersonalDayResolver` 提供）——于是"每个个人日换一次"自动成立，不需要定时器、不需要持久化。
- `rerollCount` 是「换一个」按了几次。**待决定**：它是否需要活过刷新（见 §7）。
- 同一组输入必然得到同一个地点 → 可测试、可复现、刷新不变。

架构位置（与 `docs/architecture.md` 的规则对齐）：

| 部分 | 位置 | 说明 |
| --- | --- | --- |
| 城市数据集 | `src/data/places.ts` | **不叫 Provider**。它是随仓库发布的静态内容，不是可替换的外部服务；叫 Provider 会让人以为它需要网络或降级逻辑 |
| 选择逻辑 | `src/domain/companionPlaces.ts` | 纯函数，零依赖，node --test 覆盖 |
| 展示 | `src/components/CompanionPlaces.tsx` | 只渲染，不自己抽取 |
| 时区读取 | `src/app/`（浏览器边界） | `Intl.DateTimeFormat().resolvedOptions().timeZone` + 当前日期的 UTC 偏移 |

数据集结构（草案）：

```ts
interface Place {
  id: string
  city: string          // "新加坡"
  cityEn: string        // "Singapore"，用于以后做英文界面或检索
  region: string        // 国家/地区标注，口径见 §7
  utcOffsetMinutes: number  // 480 表示 UTC+8；DST 复杂的地区见下方注意
  intro?: string        // 介绍文字，当前留空（占位）
}
```

**DST 注意**：`utcOffsetMinutes` 对多数城市是固定值，但实行夏令时的地区会随日期变化。V1 的简化方案：数据集只存**该城市的标准偏移**，并把它标为"该地的钟表读数可能因夏令时与你不同"。若以后要精确，改为存 IANA 时区名并用 `Intl` 按当前日期算偏移——**这也是为什么结构里预留 `id` 而不是直接用城市名做主键**。

## 6. 明确不做（防止范围蔓延）

- ❌ 不改变用户的真实位置，**不影响日出日落与日照计算**（那是 `Location` 的事）
- ❌ 不调用任何 API、不抓维基百科（介绍文字走静态数据集）
- ❌ 不做社交、分享、点赞
- ❌ 不做"根据你所在城市推荐活动"之类衍生物
- ❌ 不为它引入地图库

## 7. 待决定（有结论前不写代码）

1. **文案口径**：城市后面跟不跟国家/地区标注？同一个 UTC 偏移下并列的地区，标注方式需要一条一致、简洁、不引起争议的规则（例如只写城市名，或在需要时写"城市 · 地区"）。这是**编辑决策**，需要人来定，不能由代码随机决定。
2. **数据集规模与收录标准**：建议每个偏移 3–8 个、全国总量控制在 60–120 个。收录标准建议：首都 / 超大城市 / 中文语境下知名度高。谁来写介绍文字，也要定。
3. **「换一个」是否需要活过刷新**：活过刷新就要往 `StorageProvider` 加一个字段（`{ personalDayKey, rerollCount }`）；不活过刷新则纯内存即可。倾向**不持久化**，V1 从简。
4. **是否展示"当地钟表读数与你相同"这个洞察**：同一偏移下所有城市的钟表读数必然与你完全相同，这是本功能最有意思的一句话，但需要文案斟酌（避免让人误以为"那里和你作息一样"——作息是另一回事）。
5. **是否显示国旗**：国旗 emoji 在不同平台渲染不一致，且涉及地区表述问题，倾向不用。

## 8. 验收标准

1. 主卡片下方稳定显示一行"你现在生活在 UTC±X，可能的地点：<城市>"。
2. **同一天内刷新页面，城市不变**；进入下一个个人日（跨过起床时刻）后变化。
3. 点「换一个」能换到同一偏移内的另一个城市，且不会连续两次抽到同一个。
4. 点击地点展开该偏移下的城市列表；点击某个城市看到介绍（当前为占位内容）。
5. 全部逻辑可用 `node --test` 验证，不依赖浏览器。
6. 不引入任何新依赖，不产生任何网络请求（可在 DevTools Network 面板确认零请求）。

## 9. 依赖与排期

- **依赖**：`PersonalDayResolver`（✅ 第 2 步已完成，提供 `personalDayStart`，正是本功能需要的种子）。**不依赖** `Location`，因为时区以设备为准。
- **技术上现在就能做**，但按设计文档第 17–18 节的范围纪律，**不排进 V0**：V0 的完成标准是"看懂现在是我一天中的什么时候、还剩多少自然光"，这个功能与它无关，插进来只会推迟那条标准。
- **建议排期**：V0.7「趣味层」。理由：它不依赖天气/日历，可以放在 V0.5（PWA/Tauri）之后作为一次轻松的增量，也可以在 V0.2–V0.5 之间任意时刻插入，不会造成返工。
