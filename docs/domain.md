# 领域概念（domain.md）

本文件定义 NightCat 的领域语言。**概念的优先级高于实现**：先在这里把一个概念说清楚，再考虑它在哪个模块、用什么数据结构实现。

状态标记：`已确定` = 已写入设计文档且短期内不会改；`待细化` = V0 实现时需要给出精确定义；`未开始` = 后续版本才碰。

## 1. Civil Time（民用时间）— 已确定

现实世界当地时间，例如 `2026-10-12 17:00 (UTC+8)`。它是外部世界的时间基准，来自设备时钟。

要点：NightCat 内部**始终保留时区信息**。跨时区时"个人日"的边界会跟着用户的作息走，而不是跟着设备时区跳变——这个问题 V0 先记录，不实现。

## 2. Personal Time（个人时间）— 待细化

相对用户起床时刻计算的主观时间。用户 13:00 起床，则现实 17:00 表达为"起床后 4 小时"。

V0 形态：一个以起床时刻为原点的时长（`elapsed since wake`），以及可选的"个人上午/下午/晚上"标签。
待细化的问题：

- 起床时间每天都不同，是取"今天实际起床"还是"计划作息"？V0 先用计划作息。
- 如果用户还没起床，Personal Time 是负数还是"尚未开始"？倾向显式表达"尚未开始"，不用负数糊过去。

## 3. Personal Day（个人日）— 待细化

NightCat 不把午夜 00:00 当作一天的边界。一个 Personal Day 从用户的起床或设定的个人日边界开始，到下一次睡眠周期结束为止。

例：用户 `2026-10-12 13:00` 起床、`2026-10-13 05:00` 睡觉，则 `2026-10-13 03:00` 仍属于"`2026-10-12` 个人日"。

待细化的问题：

- 边界如何参数化：以"起床时刻"为准，还是允许用户单独设定"个人日切换点"（例如固定凌晨 04:00）？
- 用户连续熬夜（超过 24 小时不睡）时，个人日如何切分？

## 4. Solar / Environment Context（太阳与环境上下文）— 待细化

由地理位置与日期得到日出、日落、太阳高度等基础信息，并结合天气形成"可利用自然光窗口"。

隐私约束：位置允许用户手动选择城市，不强制精确定位。

## 5. Estimated Daylight Opportunity（预计自然光机会）— 已确定

**这是产品层估计，不是照度测量，也不代表医学效果。**

估计模型（V0 简化版）：

```text
清醒区间 ∩ 太阳位于地平线以上区间  → 再乘以天气修正因子
```

文案约束：不使用"日照剂量""补充维生素 D"等医学表述；相关界面需要注明"不构成医疗建议"。

## 6. Advice（建议）— 已确定

Advice Engine 不直接依赖某个天气 API 或某个 UI。它只消费标准化后的上下文（`DailyContext`）并产生建议，因此规则引擎、LLM 引擎、混合引擎可以互换。

V0 的三条示例规则：

1. 用户尚未起床 → 不提醒出门。
2. 剩余日照不足 60 分钟且用户清醒 → "今天自然光窗口不多了，可以考虑现在出门"。
3. 已日落 → "今日自然光窗口已结束"。

## 尚未进入领域模型的概念

计划作息 vs 实际作息（V0.3）、日程事件（V0.4）、通知策略（V0.5）、AI 生成的解释文本（V0.6）。在对应版本前不在代码里提前建模。
