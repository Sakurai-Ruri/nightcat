# 架构决策记录（decisions.md）

每条决策记录四件事：**背景 → 选项 → 决定 → 后果**。格式刻意保持轻量，等条目变多再正式化为 ADR。

---

## D-001：V0 不引入后端

- **背景**：核心功能是本地计算（个人时间、个人日）+ 公开数据查询（日出日落）。真实用户只有开发者本人。
- **选项**：① 一开始就上前端 + Node 服务 + 数据库；② 纯前端，数据留在浏览器；③ 纯前端但预留同步接口。
- **决定**：采用 ②，且不实现 ③ 的空接口。
- **后果**：没有服务器要运维，没有密钥泄露面，离线可用。代价是数据无法跨设备同步——等真的需要多设备时再引入后端（触发条件见设计文档第 11 节：多设备同步、付费 LLM、云端备份、多用户）。

## D-002：V0 用 IndexedDB，而不是 localStorage

- **背景**：需要保存作息、位置、偏好，以及少量历史记录。
- **选项**：① `localStorage`（同步 KV，5MB 上限）；② IndexedDB（异步、结构化、容量大）；③ 先用 `localStorage`，后面再迁移。
- **决定**：采用 ②，但**通过 `StorageProvider` 接口访问**，不让领域逻辑直接碰 IndexedDB。
- **后果**：异步 API 会让调用点稍复杂（每个读写都是 Promise），换来的是未来换 SQLite（Tauri）或云存储时改动被限制在 provider 一层。③ 被否掉，是因为"先 localStorage 后迁移"正好制造了一次必然的返工。

## D-003：`src/domain` 不依赖 React 与浏览器 API

- **背景**：个人时间、个人日这类计算是这个项目里最需要被信任、也最需要能独立验证的部分。
- **选项**：① 直接写在组件里或自定义 hook 里；② 独立于框架的纯函数模块。
- **决定**：采用 ②。`domain` 只包含类型与纯计算，输入输出都是普通值。
- **后果**：这些逻辑可以用固定时间数据测试，不依赖 DOM；UI 想换框架也不影响领域层。代价是多了一层类型定义和转换代码——V0 阶段这点开销可以接受。

## D-004：以 `nightcat/` 作为仓库根，而不是直接用外层目录

- **背景**：外层目录 `夜猫子神器/` 同时存放设计文档与工程。
- **决定**：工程与 Git 仓库放在 `nightcat/` 子目录（对齐设计文档第 13 节）；`docs/PROJECT_DESIGN.md` 是设计稿的副本，外层 Markdown 留作参考。
- **后果**：仓库内容干净，`nightcat/` 可以整体移动或单独发布。代价是设计文档有两份，需要约定**以仓库内 `docs/PROJECT_DESIGN.md` 为准**。

## D-005：包管理器用 npm，本机未装 pnpm

- **背景**：设计文档提到 npm 与 pnpm 都可以。
- **决定**：用 npm（本机 11.13.0 已装），只有 `package-lock.json` 一种 lockfile。
- **后果**：不引入 corepack 等额外安装步骤。若以后要换 pnpm，需要一次性替换 lockfile 并在 README 说明——不要两套 lockfile 并存。

## D-006：版本号先停在 0.0.0，第一个可用版本才叫 v0.1.0

- **背景**：设计文档的版本路线是 V0 → V0.1 → …，其中 "V0" 指可运行原型。
- **决定**：工程基线阶段保持 `package.json` 的 `0.0.0`；当 V0 完成标准达成（能设作息与位置、刷新后数据仍在、任意时刻看懂"现在是我一天中的什么时候、还剩多少自然光"）时，再定 `v0.1.0` 并打 Git tag。
- **后果**：版本号与"是否真的可用"挂钩，避免出现"版本涨了但功能没到"的虚假进度感。

## D-007：个人日边界以"起床时刻"为锚，不额外引入切换点

- **背景**：`PersonalDayResolver` 需要一个判定规则，决定任意真实时刻属于哪个个人日。两种参数化方式：以当天起床时刻为锚，或让用户单独设定一个固定切换点（如凌晨 04:00）。
- **选项**：① 起床时刻为锚；② 独立切换点；③ 两者都支持，用户可选。
- **决定**：采用 ①。个人日 = 从该日计划的起床时刻起，到下一次计划的起床时刻止。因此 `2026-10-13 03:00` 在"13:00 起床"的作息下属于 `2026-10-12` 个人日。
- **后果**：模型只有一个锚点，`PersonalDayResolver` 是纯函数，不需要额外配置项，UI 也少一个设置。代价是作息剧烈变动时边界会跟着漂移（连续熬夜、当天补觉），这些情况 V0 不处理——用户改变起床时间就等于改变了个人日边界，这是符合直觉的行为。③ 被否掉，是因为它与"V0 只解决一个问题"冲突，且缓存与历史归属的复杂度会立刻上升。

## D-008：日出日落改用在线 API（**已推翻**：原决策为本地算法）

> 状态：**Superseded by D-010**。原决策与推翻理由一并保留，因为"我当时为什么会判断错"比结论本身更值得记。

### 原决策（已废弃）

选择本地天文算法，理由归纳为三条：无网络依赖、离线可用、跨 Web/PWA/Tauri 行为一致。当时的方案对比表把权重放在"失败面"和"离线可用"两列，得出"本地算法概念更少"的结论。

### 推翻理由

1. **原论证的前提不成立**：`docs/PROJECT_DESIGN.md` 第 10 节的 V0.2 明确要接 `WeatherProvider`。天气本质上必须在线获取，所以"完全离线运行"从来不是这个项目的目标，我拿它当主要论据是错的。前提塌了，结论就不能留。
2. **取舍点放错了位置**：实测两个 API（见 D-010）后发现精度根本不是差异点——两家结果一致到分钟级。所以本地算法的真实收益不是"更准"，只是"断网时也能算"；而这一条的代价是要自己实现并校验天文公式，还要为"公式抄错但看起来算得对"设计额外的验证手段。
3. **单一数据源比省一次网络请求更值钱**：既然天气必须在线取，日出日落也从同一处取，就只有一个"今天是哪天、按哪个时区算"的权威来源；混用本地算法 + 在线天气，等于维护两套日期/时区解释。
4. **它让"剩余自然光"能在一次请求里拿到**：日出、日落、云量同响应返回，不需要拼接两次请求的时间基准。

### 保留的部分

原决策里这条判断仍然有效：**V0 的日出日落只需分钟级精度**，它服务的是"还剩多少自然光"这个量级，不是天文观测。这条现在是"API 的分钟级精度足够"的依据。

## D-010：太阳数据用 Open-Meteo，`SolarProvider` 与 `WeatherProvider` 同源

- **背景**：D-008 推翻后，需要选定具体数据源，并决定它与未来天气数据的关系。
- **实测结果**（2026-10-12 实际请求，非文档转述）：

  | 数据源 | 是否需 API Key | 返回内容 | 时区处理 | 实测值（上海 2026-10-12） |
  | --- | --- | --- | --- | --- |
  | Open-Meteo `api.open-meteo.com/v1/forecast` | **不需要** | `daily.sunrise` / `daily.sunset` / `weather_code` / `cloud_cover_mean`，可一次取回 | `timezone=Asia%2FShanghai`，响应回传 `utc_offset_seconds` 与 `timezone_abbreviation` | 日出 `05:54`，日落 `17:26` |
  | sunrise-sunset.org `/json` | 不需要 | 仅太阳数据（含各级暮光） | 固定返回 UTC，需自己换算 | 日出 `05:53:29`，日落 `17:27:50` |

- **决定**：采用 **Open-Meteo**，且 `SolarProvider` 与 `WeatherProvider` 共用同一个上游与同一次请求（V0.2 起）。
- **理由**：

  1. **无 key**：不需要注册、不在前端暴露密钥，也就不需要后端代理——这与"V0 无后端"（D-001）相容。
  2. **一次请求给全**：`daily=sunrise,sunset,weather_code,cloud_cover_mean` 已经覆盖 V0.2 的需求，避免两个数据源的时间基准不一致。
  3. **响应自带时区换算结果**：`timezone=Asia/Shanghai` 时返回的 `sunrise` 就是**当地时间字面量**（`2026-10-12T05:54`），并回传 `utc_offset_seconds`，省掉一层 UTC↔本地的手工换算——这正是本项目最容易出错的地方。
  4. 精度与备选方案一致到分钟级，因此选它不牺牲准确性。

- **后果与约束**：

  - 引入**网络失败模式**：断网、限流、字段变更。必须在 provider 层显式建模"不可用"，不允许用假数据填充（见下方"待细化"）。
  - **`timezone` 必须随位置一起保存**（IANA 名，如 `Asia/Shanghai`）。用户手动选城市时，其本地时间可能与设备时区不同，任何"按设备时区算"的假设都会在跨时区场景下出错。这条升级为 `Location` 的必填字段，见 D-011。
  - 前端直接调用第三方域名：需要一个薄封装集中处理错误格式，避免各调用点各写一份。
  - 极昼/极夜地区 `sunrise`/`sunset` 可能缺失或为 `null`，provider 必须能表达"当日无日出"而不崩。
  - **限流额度待核实**：免费层的具体调用上限尚未实测，第 4 步实现时确认并记录（本项目用量为每天数次，除非被滥用不会触及上限）。

## D-011：`Location` 必须包含 IANA 时区

- **背景**：用户可手动选择城市，所选城市可能与设备所在时区不同；而 Open-Meteo 需要 `timezone` 参数，返回的日出日落也以该时区表达。
- **决定**：`Location = { name, latitude, longitude, timeZone }`，其中 `timeZone` 为 IANA 名称字符串，与经纬度同等必填、同等持久化。
- **后果**：领域层与 provider 都不读设备时区，全部以 `Location.timeZone` 为准。这消除了"个人日边界在哪个时区判定"的歧义——第 2 步的 `PersonalDayResolver` 只做纯整数运算（约定见 `architecture.md`），时区解释全部发生在边界层（把 `Date` 转成 `TimeOfDay` 的那一处）。
- **待细化**：`Location` 的落地在第 4–5 步（`SolarProvider` 与 `StorageProvider`），第 2 步不需要它。

## D-009：测试用 Node 内置 `node --test`，不引入测试框架

- **背景**：领域层（`PersonalClock` / `PersonalDayResolver`）需要能脱离浏览器、用固定时间数据验证。
- **选项**：① Node 内置 `node --test`；② Vitest；③ Jest。
- **决定**：采用 ①。
- **实测验证**（本机 Node v24.15.0，已跑通）：

  - `node --test src/xxx.test.ts` 可直接运行 TypeScript 测试文件，**无需安装任何依赖**（Node 24 的 type stripping 默认开启）。
  - **导入必须带 `.ts` 后缀**：`import { x } from './foo.ts'` 通过；`from './foo'` 报 `ERR_MODULE_NOT_FOUND`。这条约束与本项目模板已有的 `allowImportingTsExtensions: true` 和 `verbatimModuleSyntax: true` 一致。
  - 带后缀的 `.ts` 导入同时能通过 `tsc -b` 与 `vite build`（已用真实 import 链验证，而非仅靠未被引用的孤立文件）。

- **后果**：领域层零新增依赖即可测试，符合"新依赖必须解释"的默认克制。**约定**：`src/domain/**` 与 `src/engines/**` 内部的相对导入统一写 `.ts` 后缀，保证同一份代码在 Vite 与 `node --test` 下都能解析。

  代价：`node --test` 没有 watch 模式下的 UI、没有内置的 mock 与快照能力、也不提供 DOM 环境。V0 的领域层是纯计算，这些都不需要；若将来要测 React 组件（需要 DOM），再单独评估是否引入浏览器测试方案——那是另一条决策，不在本决策范围内。

## D-012：测试用独立的 `tsconfig.test.json`，浏览器配置排除测试文件

- **背景**：第 2 步的测试用 `node:test`。`tsconfig.app.json` 的 `include: ["src"]` 把 `src/domain/*.test.ts` 也纳入了**浏览器项目**的类型检查，而该项目的 `types` 只有 `vite/client`——于是 `tsc -b` 报 `Cannot find name 'node:test'`。
- **选项**：① 往 `tsconfig.app.json` 的 `types` 加 `"node"`；② 把测试文件挪出 `src/`（如 `tests/`）；③ 新增 `tsconfig.test.json` 项目，并在 app 项目里排除测试文件。
- **决定**：采用 ③。
- **理由**：① 最省事，但它让 `process`、`Buffer` 这类 Node 全局在**浏览器代码里也变成合法**——那正是本项目最该避免的一类错误（domain 规则第 2 条要求领域层不依赖运行环境）。② 会破坏"测试与被测模块同目录"的就近原则，且 `src/` 之外的测试文件仍需要一个 `types: ["node"]` 的配置才能通过检查，等于绕一圈还是要做 ③ 的事。
- **实测确认**：`npx tsc -p tsconfig.app.json --showConfig` 显示排除前 app 项目收了 5 个文件（含 `personalTime.test.ts`），加 `exclude` 后只剩 4 个；`tsc -b` 由 4 个错误变为 0。
- **后果**：多一份配置文件要维护，且**新增测试文件必须落在 `src/**/*.test.ts` 这个模式内**，否则既不会被 `npm test` 发现，也不会被类型检查覆盖。这个模式同时写在 `package.json` 的 `test` 脚本、`tsconfig.test.json` 的 `include` 和 `tsconfig.app.json` 的 `exclude` 三处——三处必须保持一致，是已知的重复。
