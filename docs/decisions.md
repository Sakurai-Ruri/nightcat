# 架构决策记录（decisions.md）

每条决策记录四件事：**背景 → 选项 → 决定 → 后果**。格式刻意保持轻量，等条目变多再正式化为 ADR。

---

## D-001：V0 不引入后端

- **背景**：核心功能是本地计算（个人时间、个人日）+ 公开数据查询（日出日落）。真实用户只有开发者本人。
- **选项**：① 一开始就上前端 + Node 服务 + 数据库；② 纯前端，数据留在浏览器；③ 纯前端但预留同步接口。
- **决定**：采用 ②，且不实现 ③ 的空接口。
- **后果**：没有服务器要运维，没有密钥泄露面，离线可用。代价是数据无法跨设备同步——等真的需要多设备时再引入后端（触发条件见设计文档第 11 节：多设备同步、付费 LLM、云端备份、多用户）。

## D-002：V0 用 IndexedDB，而不是 localStorage

- **背景**：需要保存作息、位置、偏好，以及少量历史记录。
- **选项**：① `localStorage`（同步 KV，5MB 上限）；② IndexedDB（异步、结构化、容量大）；③ 先用 `localStorage`，后面再迁移。
- **决定**：采用 ②，但**通过 `StorageProvider` 接口访问**，不让领域逻辑直接碰 IndexedDB。
- **后果**：异步 API 会让调用点稍复杂（每个读写都是 Promise），换来的是未来换 SQLite（Tauri）或云存储时改动被限制在 provider 一层。③ 被否掉，是因为"先 localStorage 后迁移"正好制造了一次必然的返工。

## D-003：`src/domain` 不依赖 React 与浏览器 API

- **背景**：个人时间、个人日这类计算是这个项目里最需要被信任、也最需要能独立验证的部分。
- **选项**：① 直接写在组件里或自定义 hook 里；② 独立于框架的纯函数模块。
- **决定**：采用 ②。`domain` 只包含类型与纯计算，输入输出都是普通值。
- **后果**：这些逻辑可以用固定时间数据测试，不依赖 DOM；UI 想换框架也不影响领域层。代价是多了一层类型定义和转换代码——V0 阶段这点开销可以接受。

## D-004：以 `nightcat/` 作为仓库根，而不是直接用外层目录

- **背景**：外层目录 `夜猫子神器/` 同时存放设计文档与工程。
- **决定**：工程与 Git 仓库放在 `nightcat/` 子目录（对齐设计文档第 13 节）；`docs/PROJECT_DESIGN.md` 是设计稿的副本，外层 Markdown 留作参考。
- **后果**：仓库内容干净，`nightcat/` 可以整体移动或单独发布。代价是设计文档有两份，需要约定**以仓库内 `docs/PROJECT_DESIGN.md` 为准**。

## D-005：包管理器用 npm，本机未装 pnpm

- **背景**：设计文档提到 npm 与 pnpm 都可以。
- **决定**：用 npm（本机 11.13.0 已装），只有 `package-lock.json` 一种 lockfile。
- **后果**：不引入 corepack 等额外安装步骤。若以后要换 pnpm，需要一次性替换 lockfile 并在 README 说明——不要两套 lockfile 并存。

## D-006：版本号先停在 0.0.0，第一个可用版本才叫 v0.1.0

- **背景**：设计文档的版本路线是 V0 → V0.1 → …，其中 "V0" 指可运行原型。
- **决定**：工程基线阶段保持 `package.json` 的 `0.0.0`；当 V0 完成标准达成（能设作息与位置、刷新后数据仍在、任意时刻看懂"现在是我一天中的什么时候、还剩多少自然光"）时，再定 `v0.1.0` 并打 Git tag。
- **后果**：版本号与"是否真的可用"挂钩，避免出现"版本涨了但功能没到"的虚假进度感。

## D-007：个人日边界以"起床时刻"为锚，不额外引入切换点

- **背景**：`PersonalDayResolver` 需要一个判定规则，决定任意真实时刻属于哪个个人日。两种参数化方式：以当天起床时刻为锚，或让用户单独设定一个固定切换点（如凌晨 04:00）。
- **选项**：① 起床时刻为锚；② 独立切换点；③ 两者都支持，用户可选。
- **决定**：采用 ①。个人日 = 从该日计划的起床时刻起，到下一次计划的起床时刻止。因此 `2026-10-13 03:00` 在"13:00 起床"的作息下属于 `2026-10-12` 个人日。
- **后果**：模型只有一个锚点，`PersonalDayResolver` 是纯函数，不需要额外配置项，UI 也少一个设置。代价是作息剧烈变动时边界会跟着漂移（连续熬夜、当天补觉），这些情况 V0 不处理——用户改变起床时间就等于改变了个人日边界，这是符合直觉的行为。③ 被否掉，是因为它与"V0 只解决一个问题"冲突，且缓存与历史归属的复杂度会立刻上升。

## D-008：日出日落用本地算法，不调 API

- **背景**：`SolarProvider` 需要日出、日落时刻。V0 只需要这两个值（太阳高度是后续版本的事）。
- **选项对比**：

| 方案 | 网络依赖 | 新增依赖 | 代码量 | 失败模式 | 离线可用 |
| --- | --- | --- | --- | --- | --- |
| ① 本地 NOAA 算法 | 无 | 无 | 约 50–150 行（视精度） | 无（纯函数，只是数值近似） | ✅ |
| ② 公开 API（Open-Meteo 等） | 必需 | 无（用 `fetch`） | 约 20–40 行 | 断网、限流、字段变更、跨域 | ❌ |
| ③ 混合：本地 + 失败回退 API | 部分 | 无 | 约 100–200 行 | 两条路径都要测 | 部分 |

- **决定**：采用 ①。
- **理由**："哪个简洁就用哪个"在这里指向的不是**代码行数最少**，而是**概念与失败面最少**。② 的行数确实更少，但它把"能不能算出日落"变成了一件取决于网络、第三方可用性和响应格式的事，于是必须写降级逻辑、必须在 UI 上表达"数据不可用"、还要为这条路径补测试——简洁性反而被吃掉。③ 是 ② 的两倍复杂度，V0 直接排除。

  另外两点权重：V0 的哲学是离线可用（打开就该知道还剩多少自然光），且同一套代码要跑在 Web / PWA / Tauri 三种形态上，本地算法在三种形态里行为完全一致。加上 V0 无后端，走 API 等于把第三方域名写进前端。
- **后果**：第 4 步需要自己实现并校验天文算法。风险是"公式抄错但看起来算得对"，因此必须有校验手段（对照公开的日出日落时刻、检查极昼极夜边界、检查南北半球与东西经符号）。V0 的日出日落只需分钟级精度——它服务的是"还剩多少自然光"这个量级，不是天文观测。
- **待第 4 步确认**：实现后回填实际代码行数与误差校验结果。若实测精度不足以支撑"剩余自然光"的判断，再重新评估本决策。

## D-009：测试用 Node 内置 `node --test`，不引入测试框架

- **背景**：领域层（`PersonalClock` / `PersonalDayResolver`）需要能脱离浏览器、用固定时间数据验证。
- **选项**：① Node 内置 `node --test`；② Vitest；③ Jest。
- **决定**：采用 ①。
- **实测验证**（本机 Node v24.15.0，已跑通）：

  - `node --test src/xxx.test.ts` 可直接运行 TypeScript 测试文件，**无需安装任何依赖**（Node 24 的 type stripping 默认开启）。
  - **导入必须带 `.ts` 后缀**：`import { x } from './foo.ts'` 通过；`from './foo'` 报 `ERR_MODULE_NOT_FOUND`。这条约束与本项目模板已有的 `allowImportingTsExtensions: true` 和 `verbatimModuleSyntax: true` 一致。
  - 带后缀的 `.ts` 导入同时能通过 `tsc -b` 与 `vite build`（已用真实 import 链验证，而非仅靠未被引用的孤立文件）。

- **后果**：领域层零新增依赖即可测试，符合"新依赖必须解释"的默认克制。**约定**：`src/domain/**` 与 `src/engines/**` 内部的相对导入统一写 `.ts` 后缀，保证同一份代码在 Vite 与 `node --test` 下都能解析。

  代价：`node --test` 没有 watch 模式下的 UI、没有内置的 mock 与快照能力、也不提供 DOM 环境。V0 的领域层是纯计算，这些都不需要；若将来要测 React 组件（需要 DOM），再单独评估是否引入浏览器测试方案——那是另一条决策，不在本决策范围内。
